# OBS-30-001: On Suryodaya, some open deals have a stage but no usable pipeline

Seat 30 **observation**, not a bug. The instructor asked us to note it in `findings/` this way (seat chat, 24 Nov 2026, answer 7). It uses the fields of the course format (`BUG_REPORT_FORMAT.md`), and contains no passwords, tokens, customer data or platform detail.

**Steps** (read-only)
1. Log in on Suryodaya.
2. List all deals and all pipelines with the read-only list tools.
3. For each open deal (stage not closed won or closed lost), look up its stage in its pipeline.

**What we expected**
Every deal names the pipeline its stage belongs to, so the stage has a label, as on Keystone.

**What we see**
Some open Suryodaya deals have a stage key but no usable pipeline, so their stage can't be looked up and has no label. There are two kinds:
- deals with **no pipeline** at all;
- deals that **name a pipeline that doesn't exist** on the system. Their stage keys are the usual ones.

Both kinds were counted together at first; the daily snapshot check of 24 Nov told them apart.

**How the brief handles it** (agreed with the instructor, 24 Nov)
- These deals are **open**, judged by their stage key, and are ranked like any other deal.
- Each carries a data issue: "pipeline: missing, so the stage has no label", or "pipeline: not found, so the stage has no label" for a pipeline that doesn't exist. Where the brief would show the stage label (for example, in a next step's reason), it shows the stage key instead.
- Nothing is guessed: the brief doesn't assign them to a pipeline.

**Where the code handles it**
- `brief/rows.py`: builds the row with no label and adds the data issue. `stage_known` is false, as for an unknown stage, so `rows.stage_usable(row)` tells the cases apart: true for no pipeline or a pipeline that doesn't exist, false for a stage that isn't in a pipeline that does exist.
- `brief/deals.py` (Sunil, PR 2): a deal is open when `stage_usable()` is true and its stage isn't closed won or closed lost. So a deal with no usable pipeline stays open and ranked, and a deal whose stage is not in its (existing) pipeline is left out (task 3).
- `brief/changes.py`: when one of these deals leaves the list, its reason also uses `stage_usable()`, so it is "outranked by other deals", not "stage not recognised".
- Suite: task 1's recount ranks these deals like any other, and task 2 (`open_only`, Sunil, PR 2) gets an explicit check that they still count as open.
